# Design

## Context

See proposal.md (Why) for the motivation and `specs/songwriting/lyrics/spec.md` for the requirements. The existing code shapes the approach in these ways.

**The song is one JSON document, validated in two places.**
- The Rust `Song` (`backend/crates/music/src/song.rs:58-93`) is the source of truth. Its TypeScript type is generated by ts-rs into `frontend/src/generated/Song.ts`.
- The `chat` field (song.rs:87-92) is the precedent for an optional field. It uses `#[serde(default, skip_serializing_if = ...)]` with `#[ts(... optional)]`, has no `version` bump, and needs no migration.
- `Song::validate` (song.rs:708+) runs on every project create and save (`api/src/projects.rs:51-54`). The browser's `lib/song/projectFile.ts` runs a hand-written mirror of it for "Open project". `fixtures/song_validation.json` is shared by both validators, so drift between them fails tests.
- Projects store the song as a `TEXT` JSON blob, so a new field needs no database migration. The projects router already allows 2 MiB bodies (`api/src/routes.rs:28`). 20,000 characters is at most about 80 KB of UTF-8.

**Autosave watches the song object.**
- `songLibrary.autosave` (`lib/song/songLibrary.ts:448-465`) saves whenever `store.song` changes identity, debounced by 300 ms with retries. The server refuses saves that come less than one second apart. Any `set` of a new song object is therefore persisted with no extra wiring.

**Song undo is whole-song snapshots.**
- `songStore.ts` keeps `past` and `future` arrays of whole `Song` objects. Restoring a snapshot would bring back the lyrics it captured.
- The chat already handles this: it is written with a plain `set` (not an undo step, :453-455), and `withLiveChat` copies the live chat onto the restored snapshot in undo, redo, and `cancelGesture` (:527, :567, :581).

**Studio layout and shortcuts.**
- `StudioPage.tsx` puts `AssistantPanel` in the right grid column at `lg` and up (:879). Below `lg`, it opens in a `ModalDialog` drawer (:880-887).
- Global shortcuts (`components/editor/useEditorShortcuts.ts`) skip any target for which `isTextEntryTarget` is true (`lib/pianoRoll.ts:32-40`). That check already includes `contenteditable`, which covers a CodeMirror editor.
- There is no text-editor dependency yet. `TokenCounter.tsx` is the visual model for a "n / max" counter.

## Goals / Non-Goals

**Goals:**
- Lyrics persist through the existing song pipeline: autosave, project storage, and project files. No new endpoint and no new storage.
- Lyric text never enters song undo history, and song undo never changes lyrics.
- The editor is one #9 and #10 can extend rather than replace.

**Non-Goals:**
- Real-time merging of edits from two open tabs. The last save wins, subject to the existing `revision_conflict` handling.
- Server-side features that read lyrics, such as search or AI context. The server only validates the field's length.

## Decisions

### D1. `lyrics: String` on the Rust `Song`, skipped when empty
- Declare it with `#[serde(default, skip_serializing_if = "String::is_empty")]` and `#[ts(as = "Option<String>", optional)]`, mirroring `chat`.
- Skipping the empty value keeps existing songs and project files byte-identical (spec: "Empty lyrics leave the file unchanged").
- Add `pub const MAX_LYRICS_CHARS: usize = 20_000`, a `SongErrorKind::Lyrics`, and a `chars().count()` check in `Song::validate`. This yields the existing `invalid_song` 422 through the projects handler.
- Mirror the constant in `lib/song/types.ts`, add a `"lyrics"` `ProjectErrorKind`, and check with `charLength` in `projectFile.ts`. Then add a 20,000 (valid) and a 20,001 (invalid) case, including multi-byte characters, to `fixtures/song_validation.json`.
- Alternative: `Option<String>`. Rejected because it gives `None` and `Some("")` two meanings for one state.

### D2. Lyrics are a live, non-history field in the song store
- Add `setLyrics(text)` to `songStore.ts`. It writes `set({ song: { ...current, lyrics } })` with no history push, as the chat does.
- Generalize `withLiveChat` into `withLiveFields(snapshot, live)` in `songLoop.ts` (or wherever `withLiveChat` lives), so it carries both `chat` and `lyrics`. Use it at every site that already calls `withLiveChat`. A single helper means a future live field cannot be missed at one of the three sites.
- Alternative: one song-undo step per edit burst. Rejected because two undo stacks would then fight over Cmd/Ctrl+Z, and a track undo would rewind text the user is still writing.

### D3. CodeMirror 6 behind a thin React wrapper, synced with debounce
- `components/lyrics/LyricsEditor.tsx` is a client component loaded with `next/dynamic` (`ssr: false`) and created in `useEffect`.
- Extensions:
  - `history()` with `historyKeymap` and the default keymap, without `indentWithTab`, so Tab moves focus (spec: keyboard isolation).
  - `EditorView.lineWrapping`.
  - `contentAttributes` with `aria-label: "Lyrics"`.
  - A placeholder.
  - A `ViewPlugin` that adds a line decoration to lines matching `^\s*\[[^\]\n]+\]\s*$`.
  - A `changeFilter` that refuses a transaction whose resulting length passes 20,000 characters and reports it through a callback, which shows a notice.
- Edits reach the store through an update listener debounced by about 300 ms. A pending sync is flushed on blur, on unmount (tab switch or drawer close), and before the song changes. This keeps typing from creating a song object per keystroke, while the library's own debounce and retry handle the server's one-save-per-second rule.
- Opening a different song (a new `song.id`) replaces the editor state, so the notepad's undo history never crosses songs. A store change to `lyrics` for the same song that did not come from the editor (none exist today, but #9 may add one) is applied as one full-document transaction.
- Character counting uses `[...text].length` (code points), matching Rust `chars().count()`. CodeMirror's `doc.length` counts UTF-16 units, so the filter computes the code-point length only when `doc.length` passes 18,000, which keeps the common case cheap.
- Alternatives:
  - A plain `<textarea>` is simpler, but cannot style heading lines, and #10 would have to replace it to get vim bindings.
  - `@uiw/react-codemirror` lags behind React 19 peer ranges, and the wrapper it replaces is about 60 lines.
  - Monaco is several MB.

### D4. Right column becomes tabbed; narrow screens get a second drawer
- Add a small `RightColumnTabs` ("Assistant" / "Lyrics") above the right-column panel at `lg` and up. Only the selected panel mounts, except that `AssistantPanel`'s chat state already lives in `useChat` at the page level, so unmounting it loses nothing.
- The selected tab is kept in `localStorage` under `songbird.studio.rightTab`, with reads and writes wrapped in try/catch and defaulting to "Assistant".
- Below `lg`, add a "Lyrics" button beside the existing assistant drawer trigger. It opens `LyricsEditor` in the same `ModalDialog` drawer pattern.
- The tab bar and button placement are reviewed by `ui-designer` before they are built (tasks 3.1).

### D5. Heading detection is a pure function
- `lib/lyrics/headings.ts` exports `isHeadingLine(line)` and `headingLines(text)`. The decoration uses them, and #9 will reuse them for section linking.
- Both are unit-tested without a DOM.

## Risks / Trade-offs

- **[Risk] Two tabs editing the same song overwrite each other's lyrics.** → This is the same behavior as every other song edit today. `revision_conflict` surfaces it through the existing save status, and merging is a stated non-goal.
- **[Risk] Lyrics typed in the last ~300 ms are lost when the page closes.** → Flush on blur and `visibilitychange`, and rely on the library's existing pending-save handling for unload. This is the same window as other edits.
- **[Trade-off] Two undo stacks.** Cmd/Ctrl+Z means "undo text" inside the notepad and "undo arrangement" elsewhere. This matches how the song name field already behaves.
- **[Trade-off] About 150 KB (min) of CodeMirror.** It is loaded only when the Lyrics panel first opens.

## Migration Plan

The change is purely additive. Existing songs and project files load with empty lyrics, and songs without lyrics serialize unchanged. Rollback means reverting the PR. Stored songs that have lyrics keep the field in their JSON blob. The older server's `Song` type would then drop the field on the next save, since serde ignores unknown fields by default, so lyrics would be lost only for songs edited after a rollback.

After this change merges, run `/opsx:update` on #9 `add-lyrics-assistant` to remove the notepad requirements, change its capability to a modification of `songwriting/lyrics`, and depend on this change. Do the same for #10's dependency line.
