# songs/project-storage Specification

## Purpose
Stores each user's songs on the server as projects that only that user can list, open, change, or delete.

## Requirements

### Requirement: Projects are owned by one user
The system SHALL store each project as a song document (see `songs/multitrack`, "Song document") together with an owner, a `revision` number, and creation and update times. The owner SHALL be the user who created the project, and SHALL never change. Every project operation SHALL act only on projects owned by the user of the request's session. The only exception SHALL be share links (see `songs/share-links`): an active share link gives anyone holding its token read-only access to the shared song projection of that one project, and nothing else about it or its owner. A share link SHALL NOT allow listing, saving, or deleting any project. A project owned by someone else SHALL be treated exactly as one that does not exist: `404` with code `not_found`, with the same response body and no difference in behavior, for every method. In particular, a save to another user's project SHALL get `404` whatever `revision` it sends, and never `409`, so that the response cannot reveal that the id exists.

#### Scenario: Another user's project is invisible
- **WHEN** user B requests `GET /api/v1/projects/{id}` for a project owned by user A
- **THEN** the response is `404` with code `not_found`, the same as for an id that was never used

#### Scenario: Shared project still invisible through the project API
- **WHEN** user A has an active share link for a project, and user B requests `GET /api/v1/projects/{id}` for it
- **THEN** the response is `404` with code `not_found`

#### Scenario: Cannot overwrite another user's project
- **WHEN** user B sends `PUT /api/v1/projects/{id}` for user A's project
- **THEN** the response is `404`, and user A's project is unchanged

#### Scenario: Stale revision on another user's project still 404
- **WHEN** user A's project is at revision 4, and user B sends `PUT /api/v1/projects/{id}` for it with revision 1, then with revision 4
- **THEN** both responses are `404` with code `not_found`, neither is `409`, and user A's project is still at revision 4

#### Scenario: Cannot delete another user's project
- **WHEN** user B sends `DELETE /api/v1/projects/{id}` for user A's project
- **THEN** the response is `404` with code `not_found`, and user A can still open the project

### Requirement: List projects
`GET /api/v1/projects` SHALL respond `200` with `{"projects": [...]}`. The list SHALL hold one entry per project owned by the current user, and no others, each with `id`, `name`, `time_signature`, `track_count`, `revision`, and `updated_at`, most recently updated first. It SHALL NOT include song contents.

#### Scenario: Only my projects
- **WHEN** user A owns "Late Train" and user B owns "Morning", and user A lists projects
- **THEN** the list contains "Late Train" and not "Morning"

### Requirement: Create a project
`POST /api/v1/projects` SHALL accept `{"song": <song document>}`. When the song is valid, it SHALL store a new project owned by the current user, with a new id generated by the server, and SHALL respond `201` with `{"project": {"id", "revision", "updated_at", "song"}}`, where the stored song's `id` equals the project id. Any `id` sent by the client SHALL be ignored, so that a client cannot choose an id that collides with another user's project. Each user SHALL be limited to 500 projects and to 100 MiB of stored songs in total. A create that would exceed either limit SHALL be refused with `409` and code `project_limit`, storing nothing. The limits SHALL hold even when several creates for the same user arrive at once.

#### Scenario: Create
- **WHEN** a signed-in user posts a valid song named "Late Train"
- **THEN** the response is `201` with a new project id and revision 1, and the project appears in that user's list

#### Scenario: Client id ignored
- **WHEN** a user posts a song whose `id` equals the id of another user's project
- **THEN** a new project with a different id is created, and the other project is unchanged

#### Scenario: Concurrent creates respect the limit
- **WHEN** a user who owns 499 projects sends two creates at the same moment
- **THEN** one gets `201`, the other gets `409` with code `project_limit`, and the user owns exactly 500 projects

#### Scenario: Storage quota
- **WHEN** a user's projects already hold close to 100 MiB of songs and they create a project that would take the total over
- **THEN** the response is `409` with code `project_limit`, and no project is created

### Requirement: Open a project
`GET /api/v1/projects/{id}` SHALL respond `200` with `{"project": {"id", "revision", "updated_at", "song"}}` for a project the current user owns. The song SHALL be returned exactly as last saved, including fields this version of the service does not recognise.

#### Scenario: Unknown fields survive storage
- **WHEN** a user saves a song containing an extra field `"mood": "wistful"` and opens it again
- **THEN** the returned song still contains `"mood": "wistful"`

### Requirement: Save a project
`PUT /api/v1/projects/{id}` SHALL accept `{"song": <song document>, "revision": <number>}`, where `revision` is the revision the client last loaded or saved. When the revision matches the stored one, the song is valid, and the song's `id` equals the project id, the server SHALL replace the stored song, increase `revision` by 1, and respond `200` with the new `revision` and `updated_at`. When the stored revision is newer, the server SHALL respond `409` with code `revision_conflict` and SHALL NOT change the project. When the song's `id` differs from the project id, the server SHALL respond `422` with code `id_mismatch` and SHALL NOT change the project. A save that would take the user over the storage limit SHALL be refused with `409` and code `project_limit`. A save that arrives less than one second after the previous successful save of the same project SHALL be refused with `429`, code `too_many_requests`, and a `Retry-After` header, and SHALL NOT change the project. Saving or deleting an id the user does not own, or that does not exist, SHALL respond `404` with code `not_found`.

#### Scenario: Save
- **WHEN** a user saves revision 3 of their project with a changed tempo
- **THEN** the response is `200` with revision 4, and opening the project shows the new tempo

#### Scenario: Stale save refused
- **WHEN** the project was saved as revision 4 from one tab, and another tab saves with revision 3
- **THEN** the second save gets `409` with code `revision_conflict`, and revision 4 is unchanged

#### Scenario: Mismatched song id refused
- **WHEN** a user sends `PUT /api/v1/projects/{id}` with a song whose `id` is a different project's id
- **THEN** the response is `422` with code `id_mismatch`, and neither project changes

#### Scenario: Saves too close together
- **WHEN** a user saves a project and saves it again 200 ms later
- **THEN** the second save gets `429` with code `too_many_requests` and a `Retry-After` header, and the project keeps the first save's contents and revision

### Requirement: Delete a project
`DELETE /api/v1/projects/{id}` SHALL permanently delete a project the current user owns, together with its share links, their snapshots, and their comments, and respond `204`. For an id that does not exist or is owned by another user, it SHALL respond `404` with code `not_found`.

#### Scenario: Delete
- **WHEN** a user deletes their project "Demo"
- **THEN** the response is `204`, and "Demo" no longer appears in their list or opens

#### Scenario: Delete a shared project
- **WHEN** a user deletes a project that has an active share link with comments
- **THEN** the response is `204`, the link's listen API responds `404` with code `not_found`, and the comments no longer exist

#### Scenario: Delete a missing project
- **WHEN** a user sends `DELETE /api/v1/projects/{id}` for an id that was never used
- **THEN** the response is `404` with code `not_found`

### Requirement: Project validation
The create and save endpoints SHALL validate the song with the same rules as song export (see `songs/export`, "Song validation for export"), and SHALL reject an invalid song with `422` and the same error codes and messages, storing nothing. Bodies that are not valid JSON or are missing `song` or `revision` SHALL be rejected with `400`.

#### Scenario: Invalid song refused
- **WHEN** a user saves a song in which two clips on the same track overlap
- **THEN** the response is `422` with code `invalid_song`, and the stored project is unchanged
